## 2. Dependency graph

```
index.html  (source of truth: 21 tracks' content + full JS engine + CSS, inline)
     │  node build.js
     ▼
 ┌───────────────────┬────────────────────────┬─────────────────────────┐
 ▼                    ▼                        ▼                        ▼
public/css/main.css  public/js/engine.js   src/_includes/tracks/*.html  (baseNjk string,
(168 KB, extracted)  (extracted <script>)  (21 files, per-track HTML)   written to
                                                                          src/_includes/base.njk)
                                                     │
                                                     ▼ npx @11ty/eleventy
                                              _site/{track}/index.html × 21
                                              (+ passthrough-copied static files)
                                                     │
                                              GitHub Actions → gh-pages
```

Runtime (browser) dependency edges, from `index.html`'s own `<script src>` tags:
- MathJax: **3 separate CDN `<script>` tags** (`mathjax@3.2.2/es5/tex-svg.js` on jsdelivr, `mathjax/3.2.2/es5/tex-mml-chtml.js` and `tex-svg.js` on cdnjs, plus a `mathjax@3` unpinned tag) — down from the 7 found in the 2026-07 audit, but still redundant; only one build should load.
- JSZip (cdnjs), Google `apis.google.com/js/platform.js`.
- `bank-data/{track}.json` fetched client-side at quiz-generation time (not build-time).
- Supabase client + `cloud-sync.js`/`cloud-config.js`/`teacher-view.js` for the optional account features.

**Cycle found (soft, by design, already documented as a bug source):** the shared footer/nav markup is hand-duplicated in two places — the standalone `index.html` and the `baseNjk` string inside `build.js` — because `index.html` needs to preview correctly on its own during editing, but the *built* site's shell comes from `baseNjk`, not from `index.html`'s own `<head>`/`<footer>`. A change to one without the matching change to the other makes the root page and the track pages visibly diverge. `CLAUDE_CODE_STARTER_PROMPT.md` confirms this "has caused real bugs before." This is the single highest-value target for Phase 1's "aggressive de-duplication" principle.

**Orphan edge:** `sw.js`'s precache list references `course-loader.js`, `router.js`, `storage.js`, `desmos-widget.js` — none of which any HTML page actually loads. The service worker will precache four files nothing ever requests.

## 5. Content/logic entanglement

This is the single biggest finding, and it is **by design, not oversight** — worth stating precisely rather than just flagging as a problem:

- All educational content (21 tracks × chapters × definitions/theorems/examples × MCQ generation logic × the entire interactive-explorer JS engine) lives inside **one 41,067-line HTML file**. `CLAUDE_CODE_STARTER_PROMPT.md` calls this the "golden rule": `index.html` is the only source of truth; everything downstream is generated.
- Consequence for Objective A (human maintainability): adding or editing a lesson means editing `index.html` directly — there is no separate content/data layer for lesson prose (there IS one for MCQ question banks — `bank-data/*.json` — which is the one place content ⟂ logic already holds).
- Consequence for Objective B (token economy): any agent task that touches lesson content must locate and edit a specific region inside a 3.49 MB / ~870K-token file. A grep-first agent can scope this down to the relevant chapter; an agent that reads the file naively pays the full cost. See §6.
- The **quiz/MCQ layer already follows the target pattern** (`bank-data/{track}.json`, pure data, fetched at runtime, zero code changes to add a question) — this is proof the pattern works here and isn't a hypothetical; it just hasn't been extended to lesson prose/explorers yet.

## 6. Hard-coded values

- **Colors:** 215 distinct hex values in `public/css/main.css` outside the 87-token layer (§3). No secrets scan hit found any hardcoded API key, password, or token string in tracked `.js`/`.html`/`.njk` files — `app.py`'s `ANTHROPIC_API_KEY` is correctly sourced from an environment variable, not hardcoded. **No secrets flagged.**
- **Cache-busting:** every content PR manually bumps a version string in 3 separate files (`public/css/main.css`, `public/js/engine.js`, `sw.js`'s `SW_VERSION`) — confirmed by inspecting the last 4 merged PRs, every one of which touched exactly these 3 files alongside the real content change. This is a manual, repeatable, mechanical step currently done by hand on every content PR — a candidate for either automation or a documented recipe step (see Phase 1 principle #12, deterministic quality gates).
- **URLs:** `pathPrefix: "/ClipSAT/"` hardcoded once in `.eleventy.js` (single source, fine) and the live URL hardcoded again in `build.js`'s `baseNjk` (`https://mohammedamy.github.io/ClipSAT{{...}}` for the canonical tag) and in `sw.js`/`manifest.json`. Not flagged as urgent, but 3+ places know the site's own base URL.

## 8. Token-cost baseline (Appendix A benchmark tasks)

**Methodology:** tokens estimated at ~4 bytes/token (standard heuristic). "Naive" = an agent with no repo-specific guidance reads full files it touches. "Grep-first" = an agent that locates the relevant section before reading (what an experienced session — or one following `CLAUDE_CODE_STARTER_PROMPT.md` — actually does today; evidenced by the last 4 real Arabic-translation PRs, all of which landed as clean, scoped diffs against `index.html` without needing to touch it wholesale). Both are reported because the gap between them **is** the token-efficiency problem this re-engineering effort exists to close — a well-briefed agent already avoids much of the naive cost; an unbriefed one does not, and nothing in the repo enforces the good path.

| # | Task (adapted to ClipSAT) | Files to read (naive → grep-first) | Tokens to read (naive → grep-first, approx.) | Files to edit | Human wall-clock estimate |
|---|---|---|---|---|---|
| 1 | Add a new lesson/chapter to an existing track, EN+AR | 1 → 1 (targeted region of `index.html`) | ~870K → ~15–40K | `index.html` (+4 mechanical: `main.css`, `engine.js`, `sw.js` version bumps, `tracks/{track}.html` regenerated by build script, not hand-edited) | 30–90 min (real content authoring, not mechanics) |
| 2 | Add an entirely new course/track with 5 lessons | 3 → 3 (`index.html`, `build.js`'s track-ID list, `.eleventy.js`/`sitemap.xml`) | ~870K+50K → ~60–100K | `index.html`, new `src/{track}/index.njk` (8-line copy of an existing one), `sitemap.xml`, `build.js` (track list), new `bank-data/{track}.json` | Several hours (new content + new question bank) |
| 3 | Change primary brand color + heading typeface site-wide | 1 → 1 (`public/css/main.css`) | ~42K → ~42K (file is generated but token layer means edits stay localized to token declarations) | 1 file if only the 87 tokens are touched; **but** 215 hardcoded hex values mean a *complete* rebrand also needs a find-and-fix pass across the same file | 15 min (tokens only) to 2+ hrs (if hardcoded colors must be hunted down too) |
| 4 | Add a new question type to the quiz/practice module | 2–3 → 2 (`index.html`'s quiz-generation JS region, `bank-data` schema) | ~870K → ~80–150K | `index.html` (engine logic), potentially all 21 `bank-data/*.json` if the new type needs new fields | Half a day+ (engine change, not content change) |
| 5 | Fix a layout defect in Arabic RTL on mobile | 1–2 → 1 (`public/css/main.css`, possibly `index.html` for structural HTML) | ~42K–870K → ~20–42K | `public/css/main.css` typically; `index.html` if structural | 30–60 min (matches actual pattern from the dark-mode-contrast-sweep PRs in memory) |
| 6 | Embed a new video into an existing lesson | 1 → 1 (targeted region of `index.html`) | ~870K → ~10K | `index.html` (+ same 4 mechanical files as task 1) | 10–20 min |
| 7 | Add a new top-level nav item + landing page | 4 → 4 (`index.html` nav markup, `build.js`'s `baseNjk` nav markup — **both**, per §2's duplication finding — `.eleventy.js`, `sitemap.xml`) | ~870K+50K → ~60K | 4 files, of which the 2-places-for-nav duplication (§2) is a direct tax on this exact task | 45–90 min |
| 8 | Update site-wide footer (links, contact, social) | 2 → 2 (`index.html` footer, `build.js`'s `baseNjk` footer — **both**, same duplication) | ~870K+50K → ~40K | 2 files, must stay in sync by hand | 20–40 min, with real risk of the two drifting (documented past bug) |
| 9 | Add structured data/SEO metadata to a lesson page type | 1 → 1 (`build.js`'s `baseNjk` JSON-LD block) | ~50K → ~10K | 1 file (`build.js`) — this one's already well-factored, single edit point | 20–30 min |
| 10 | Translate an existing English-only page into Arabic | 1 → 1 (targeted `index.html` region) | ~870K → ~15–40K | Same pattern as task 1 — this is the exact task type evidenced by the last 4 merged PRs | 1–3 hrs (real translation work, not mechanics) |

**Aggregate read:** for a naive agent, 8 of 10 tasks require paying some fraction of the ~870K-token `index.html` cost because there is no smaller file that scopes the content. For a grep-first agent (the realistic case today, given `CLAUDE_CODE_STARTER_PROMPT.md` exists), the median task reads on the order of 15–60K tokens — **already a >90% reduction from naive**, achieved not by architecture but by a human-written briefing document plus grep discipline. The architectural gap is that this reduction is *not enforced or structural* — nothing prevents a future session from reading `index.html` wholesale, and two tasks (7, 8 — nav and footer) pay a duplication tax that structure alone (not discipline) could remove.

## 9. Risk register — five things most likely to break during any further migration

1. **The `index.html` ⟷ `build.js`/`baseNjk` dual-edit requirement (footer/nav).** Already caused a real, shipped bug once. Any restructuring that touches page shell markup must not introduce a *third* place to remember.
2. **`.eleventy.js` passthrough-copy omissions.** Already caused a real, shipped bug once (standalone pages silently missing from `_site/`). Same risk class as #1: a manual "remember to register it here too" step.
3. **Cache-busting version bumps done by hand across 3 files per PR.** Not yet a documented bug, but it's a manual step with no verification gate — a missed bump means users see stale `engine.js`/`main.css` for up to their 10-minute cache window after a real fix ships.
4. **MathJax duplicate/unpinned loads.** Down from 7 to 3–4 script tags since 2026-07, still not resolved; any performance work (Phase 6 Lighthouse targets) will hit this immediately.
5. **`app.py` (the chat backend) is entirely outside this repo's build/deploy pipeline.** Any re-architecture that assumes "the site" means "what GitHub Actions builds" will silently miss this component. It needs its own hosting story, and none of the phases in `clipsat_reengineering_prompt.md` currently account for a second deployable.

---

## Executive summary — five structural pathologies, ranked by cost

1. **Content/logic entanglement in `index.html` (41K LOC / 3.49 MB).** The dominant token-cost driver (§5, §8) and the reason most benchmark tasks touch a multi-hundred-thousand-token file at all, even though grep discipline currently masks most of the pain. This is the same finding as 2026-07's audit — it has not been resolved, only worked around by the Eleventy extraction layer sitting downstream of it.
2. **Two structural "remember to edit it in a second place" traps** — footer/nav (`index.html` vs. `baseNjk`) and standalone-page passthrough registration (`.eleventy.js`) — both already confirmed to have caused real shipped bugs, not hypothetical risk.
3. **Design-token layer exists but isn't authoritative** — 87 real CSS custom properties coexist with 215 hardcoded hex values in the same file, so "change the brand color" (benchmark task 3) is a 1-file-if-lucky, 2-hour-hunt-if-not task.
4. **No enforced token-efficiency guardrails.** The actual >90% token reduction achieved today (§8) comes entirely from a human-maintained briefing doc (`CLAUDE_CODE_STARTER_PROMPT.md`) and agent grep discipline, not from repo structure. Nothing stops regression to naive full-file reads, and nothing like `docs/RECIPES.md` exists yet to make the good path the *only* obvious path.
5. **1,366 LOC of dead code shipped and precached** (`course-loader.js`, `router.js`, `storage.js`, `desmos-widget.js`) plus a second deployable (`app.py`) that lives outside the build graph entirely — both invisible to anyone reading only the build pipeline, both worth resolving before they're mistaken for load-bearing.
